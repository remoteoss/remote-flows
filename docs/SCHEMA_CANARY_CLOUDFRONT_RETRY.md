# Schema canary: retrying CloudFront blocks

Plan only. No code ships with this document.

## Problem

The nightly schema canary talks to the sandbox gateway through CloudFront. Under load, CloudFront sometimes answers with an HTML `403 Request blocked` page instead of the API response. The canary records this as a failure, so a block looks the same as a real schema regression.

In a recent run, 6 of 8 reported failures were blocks and only 2 were real schema failures. A rerun after about 2 minutes normally clears a block.

Today the only retry in the canary is the exponential backoff when archiving employments. Every other call (seed, PATCH, GET, contract-eligibility, submit) fails on the first block.

## Goals

- A block does not turn into a reported failure unless it persists.
- Real failures (schema validation, API errors) are never retried or hidden.
- Blocks that survive all retries are labelled as blocked, not failed.
- No change to the SDK's public API or to anything under `src/`.

## Non-goals

- Retrying real API errors, validation errors or 5xx responses on non-idempotent calls.
- Changing how schemas are fetched or compared.
- Making the sandbox itself more tolerant of load.

## Design

### 1. Retry at the client layer

The canary builds its API clients in one place (`scripts/schema-canary/auth.ts`). Giving those clients a custom `fetch` that retries covers every call at once, including endpoints that get blocked on one run and not the next.

The retry lives in `scripts/schema-canary/` and does not touch the SDK client.

### 2. What is retryable

| Response                                   | Retry                   |
| ------------------------------------------ | ----------------------- |
| 403 whose body is the CloudFront HTML page | Yes, for every method   |
| Network error thrown by `fetch`            | Idempotent methods only |
| 429, 502, 503, 504                         | Idempotent methods only |
| 403 with a JSON body                       | No                      |
| Any other 4xx                              | No                      |

A CloudFront block means the request never reached the origin, so replaying a POST or PATCH is safe. A 5xx or a timeout on a POST or PATCH may mean the first attempt was applied, so those are not retried.

Detection matches the CloudFront signature in the body (`Generated by cloudfront`), not the status code alone, so a real API 403 is never retried.

### 3. Backoff

- 4 to 5 attempts per call.
- Exponential backoff starting around 15s, capped around 60s, with jitter.
- A total retry budget per call so a bad night cannot hang the workflow.

The short 1s, 2s, 4s schedule would give up well before a block clears.

### 4. Shared cool-down

The canary runs with a concurrency of 6. When one worker is blocked, the other five keep sending requests and can extend the block.

When a worker sees a CloudFront block, it sets a shared cool-down. Every worker waits for the cool-down to expire before sending its next request, then proceeds. This is the part most likely to reduce the number of blocks, rather than only recover from them.

### 5. Lower request pressure

Evaluate two options after steps 1 to 4 are in:

- Lower the default concurrency from 6.
- Add a small shared rate limiter in front of the client.

Only add these if blocks still reach the report after retries and cool-down.

### 6. Reporting

- Record the number of retries per entry, or at least log it, so a country that only passes after retries stays visible.
- When retries are exhausted, record the entry with the outcome `blocked` instead of `fail`, keeping the error text.
- The report title counts only real failures, and blocked entries are listed separately.

This changes the report format, so it is a separate step (see the rollout).

## Rollout

1. **Client retry and cool-down.** Retry on the CloudFront signature, with backoff and the shared cool-down. No report change.
2. **Blocked outcome.** Add `blocked` to the report and update the workflow steps that read the report (failure summary, issue filing, PR title) so blocked entries do not open or update failure issues on their own.
3. **Tune pressure.** Look at a week of nightly runs. If blocks still appear, lower concurrency or add the rate limiter.

Each step is its own PR.

## Testing

Per the repo's testing rules, with vitest and MSW:

- The handler returns the CloudFront HTML 403 N times, then a 200. The call succeeds and was attempted N + 1 times.
- The handler returns a JSON 403. The call fails after one attempt.
- A POST that gets a 503 is not retried.
- Retries exhausted: the error carries the blocked classification.
- Cool-down: while one call is waiting, a second concurrent call does not send a request.

Each test must fail with the behaviour removed (for example, with the retry disabled), and the PR's Testing section says what was removed.

Timing uses `vi.useFakeTimers()`, with no real sleeps.

## Open questions

1. Is retrying only at the client layer enough, or should a whole country be re-run when it still ends up blocked?
2. Is the `blocked` outcome worth the report format change, given the issue-filing logic in the workflow reads that report?
3. Is a total retry budget per call or per run the better limit for the nightly job's runtime?
