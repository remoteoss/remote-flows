Partner integration guide

DailySchedule Component

The default UI rendered for the daily_schedule field — and the one piece a partner replaces when they override it via jsfModify.contract_details.fields.daily_schedule['x-jsf-presentation'].Component. This walks through what it does, what it delegates, and what's now exported so a replacement doesn't start from zero.

Why this file specifically

src/flows/Onboarding/components/DailySchedule/DailySchedule.tsx is markup only — every rule about what's valid and what gets saved lives elsewhere. That split means a partner swapping in their own UI isn't reimplementing validation from scratch; they're building a different presentation over the same data and behavior. The library still resolves schema metadata, form context, and defaults for them either way — see the diagram below.

Where a replacement sits

DailyScheduleContainer always runs — flag on, custom UI or not. It's the thing that turns raw schema metadata into the DailyScheduleRenderProps object every UI receives. A custom Component replaces only the box on the right.

Anatomy of the file

Six pieces, in the order they appear:

DAY_LABELS

A Weekday → "Monday" lookup for the header row and checkbox labels. The only hardcoded copy in the file.

DailyScheduleSummarySegments

Renders one summary line's { text, bold? } segments — the formatting buildDailyScheduleSummary returns, turned into <strong> where flagged.

DailyScheduleSummaryBody

The grouped work-hours/break lines + weekly total. Shared verbatim between the read-only summary and the edit modal's live preview, so both always agree.

DailyScheduleHoursErrorBanner

Renders getDailyScheduleHoursError's result, or nothing. Shown in both the summary and the modal.

DailyScheduleEditForm

The modal body: calls useDailyScheduleEditForm for state/validation/save, then renders a checkbox + two time fields + a break-duration field per day, the live preview, and Save / Cancel / Reset.

DailySchedule exported

The default export: read-only summary + badge + "Edit schedule" trigger, and the Dialog hosting DailyScheduleEditForm.

What you'd own vs. what's already done

Rebuilding this component means rebuilding the six pieces above — markup, styling, your own modal primitive. It does not mean rebuilding any of this:

You reimplementThe library already did
Read-only summary markup, badge, modal chrome buildDailyScheduleSummary — grouping consecutive days + shared times/breaks into lines, and the weekly total
Per-day row layout (checkbox + start/end/break inputs) useDailyScheduleEditForm — react-hook-form wiring, Zod validation (HH:mm format, required-on-checked, "at least one day"), save mapping, reset-to-default
Hours-error copy placement / styling getDailyScheduleHoursError — the country/schedule-aware weekly-range check and its message
Defaulting UX (e.g. showing an empty state) resolveDailyScheduleValue — saved value, or the metadata's default schedule when there isn't one yet

What's now exported

These were previously internal to the package — reachable by DailySchedule.tsx itself but not by a consumer. They're now exported from both src/flows/Onboarding/index.ts and the package root, so they're importable as: 

import {
  useDailyScheduleEditForm,
  buildDailyScheduleSummary,
  calculateWorkingHours,
  getDailyScheduleHoursError,
  resolveDailyScheduleValue,
} from '@remoteoss/remote-flows';

import type {
  DailyScheduleRenderProps,
  DailyScheduleValue,
  DailyScheduleSummaryDay,
  UseDailyScheduleEditFormOptions,
} from '@remoteoss/remote-flows';

A minimal replacement, using the exported pieces instead of hand-rolling them: 

function MyDailySchedule(props: DailyScheduleRenderProps) {
  const { previewDays, hoursError, handleSave /* ...*/ } =
    useDailyScheduleEditForm(props);

  const { workHoursLines, totalWeeklyHours } =
    buildDailyScheduleSummary(previewDays, props.subtractBreaksFromWorkHours);

  // render workHoursLines / totalWeeklyHours / hoursError however you like
}

Not exported, and not needed: DailyScheduleContainer, getDefaultsFromSchema, getWorkHoursBounds. Your Component override is mounted inside the container (see the diagram above) — it receives already-resolved DailyScheduleRenderProps, so it never needs the schema-metadata derivation itself.
