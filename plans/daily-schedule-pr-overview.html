01 Why this shape

daily_schedule is one JSON-schema field, but it stands in for seven per-day time triples plus a derived weekly-hours validity check — too much for the generic nested-fieldset renderer to present well. Dragon solved the same problem with a dedicated component; this PR ports that UX rather than reinventing it.

The field only renders through this path when a consumer opts in via options.features: ['daily_schedule'] — everyone else keeps the existing generic field UI, so this ships with zero behavior change for current integrators.

Reference: Dragon's WorkScheduleFieldForJSONSchema (employ-starbase/dragon MR !49203). Design notes live in plans/daily-schedule-field.md.

02 How it's wired

useOnboarding() (src/flows/Onboarding/hooks.tsx) injects the field only when the flag is on, and — this is the extensibility point the rest of the PR is built around — always renders through DailyScheduleContainer first, so a consumer override never has to redo the schema/metadata derivation.

03 Data layer

Everything that decides what's valid and what to save is framework-agnostic — no JSX — so it's testable in isolation and reusable by any replacement UI.

components/DailySchedule/types.ts new +106

The contracts: Weekday, DayHours, DailyScheduleValue (the shape written back to the field), WorkHoursRange, DailyScheduleMetadata (the raw schema x-jsf-presentation.metadata block), and the composite DailyScheduleRenderProps every UI — default or custom — is handed.

components/DailySchedule/utils.ts new +474

Ported from Dragon's schedule.js / time.js. Pure functions:

  • calculateWorkingHours — start/end/break → hours for one day
  • getDefaultsFromSchema / getWorkHoursBounds — metadata → camelCase defaults + the allowed weekly-hours range for the current work schedule
  • resolveDailyScheduleValue — saved value, or a schedule built from default_schedule when there isn't one yet
  • buildDailyScheduleSummary — groups selected days into Dragon-style lines ("Monday to Friday, from 09h00 to 18h00") plus the weekly total
  • getDailyScheduleHoursError — flags a total outside the country/schedule's allowed range
components/DailySchedule/useDailyScheduleEditForm.ts new +306

The headless edit-form: react-hook-form + a Zod schema encoding every validation rule (HH:mm format, required fields on checked days, "at least one work day"), plus the save mapping (mapDailyScheduleEditFormDataToValue) and reset-to-default logic. Its own doc comment is explicit that a fully custom UI should call this hook rather than re-deriving the rules.
