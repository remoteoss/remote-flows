Daily Schedule Field

A headless container and a validation hook that give partners building custom onboarding UIs the same schema-driven defaults, hour-bounds, and save logic Dragon's WorkScheduleFieldForJSONSchema already computes — without registering a new field type, and without touching Dragon.

Scope

Three things named "schedule," only one of them this

The plan is explicit that this is not a Dragon migration and not a rebuild of the existing, unrelated work-schedule field type. Keeping the three apart matters more than it sounds:

untouched

Dragon's WorkScheduleFieldForJSONSchema

Formik-based, lives in employ-starbase. Ground truth for the UX this plan matches. Never consumes remote-flows — no migration happening here.

untouched

the work-schedule field type

Already in remote-flows, already RHF-based — but a flat, schema-metadata-blind DailySchedule[] shape. Unused in production. Not retrofitted.

this PR

daily_schedule

New: a headless container + reusable validation hook, swapped in over the field's existing generic-fieldset rendering via jsfModify.

Where it lives

The schema already carries the answer

Tiger sends daily_schedule as an ordinary fieldset, but its x-jsf-presentation carries a metadata block with everything a UI needs to render sensible defaults and enforce hour bounds — country name, default times, which days are available, and the weekly-hour range per work-schedule type. Nothing here needed inventing; it only needed reading correctly.

daily_schedule['x-jsf-presentation'] — Germany contract-details schema (real fixture) 
{
  "inputType": "fieldset",
  "metadata": {
    "country_name": "Germany",
    "default_start_time": "09:00",
    "default_end_time": "18:00",
    "default_break_duration_minutes": 60,
    "subtract_breaks_in_work_hours": true,
    "work_days": ["monday", "tuesday", "…", "saturday"],
    "default_schedule": [
      { "day": "monday", "start_time": "09:00", "end_time": "18:00", "break_duration_minutes": 60, "hours": 8 }
      // … tuesday–friday, same shape
    ],
    "work_hours_per_week": {
      "baseline":  { "minimum": 1,  "maximum": 48 },
      "full_time": { "minimum": 31, "maximum": 48 },
      "part_time": { "minimum": 1,  "maximum": 30 }
    }
  }
}

Confirmed empirically against json-schema-form's field builder: every key under x-jsf-presentation except inputType is merged directly onto the field object — so this whole block arrives at the container as field.metadata, not nested under scopedJsonSchema as originally guessed in the plan.

Architecture

One hook, two possible UIs

The container owns every schema derivation. The validation hook owns every rule about what a valid schedule is. The default UI is markup wired to both — and so is any consumer's own UI, if they replace it.

Dashed = not built yet (Phase 4). The property being protected: whichever UI renders — ours or a consumer's — it goes through the same useDailyScheduleEditForm, so the library, not each integrator, decides what a valid schedule looks like.

Data flow

Edit, validate, one write

Dragon's version wrote per-field as the user typed. Here, the whole { selected_days, schedule } object is written back exactly once, on a successful save — which is also why Dragon's "only validate on the last field update" workaround wasn't needed here. 

sequenceDiagram
    actor Employer
    participant UI as DailySchedule (modal)
    participant Hook as useDailyScheduleEditForm
    participant Field as daily_schedule field value

    Employer->>UI: click "Edit schedule"
    UI->>Hook: open with current value (or schema defaults if unset)
    Hook-->>UI: form rows: one per available work day
    Employer->>UI: toggle days, edit start/end/break
    Employer->>UI: click "Save schedule"
    UI->>Hook: handleSave()
    Hook->>Hook: validate with dailyScheduleEditFormSchema (zod)
    alt schedule invalid
        Hook-->>UI: rootError ("Select at least one work day", etc.)
        UI-->>Employer: inline error, modal stays open
    else schedule valid
        Hook->>Field: setValue({ selected_days, schedule })
        Field-->>UI: onSaved() closes the modal
    end

One setValue call per save — never one write per field or per day.

Decisions

What was chosen, and why

Container + jsfModify override,
not a new field type
Mirrors paid_time_off_info in Termination exactly — a documented, shipped pattern ("Method 3: Field-Specific Override," docs/COMPONENT_CUSTOMIZATION.md) — instead of teaching jsfModify to rewrite inputType and registering daily_schedule as a globally swappable type reachable from every flow.
Tradeoff: customization goes through jsfModify.fields.daily_schedule, not the global components prop — same limitation annual_gross_salary already has.
Validation extracted into
useDailyScheduleEditForm
The first pass put react-hook-form + schema validation directly inside the default UI component. A consumer swapping in their own UI would've had to reinvent every rule from scratch — and could quietly diverge from what counts as valid.
Now: the hook is the single source of truth for defaults, validation, and the save mapping; both the shipped UI and any custom one call it.
zod for this one form,
not the repo's usual Yup
A deliberate, scoped exception. This edit-modal form is entirely local — it never touches json-schema-form-kit's own Yup-based resolver — so there's no compatibility concern, only a second validation library now shipping in the bundle.
Worth revisiting: a size-check glance in Phase 6.
Phase 4 will not fully mirror
paid_time_off_info's override
PTO lets a consumer-supplied Component fully replace the field, bypassing the container — fine there, since PTO's queries barely depend on what renders. Not fine here: a full bypass would force a custom UI to reimplement schema derivation and validation from raw field props.
Plan: always route through DailyScheduleContainer; treat a consumer's Component as the render function instead.
